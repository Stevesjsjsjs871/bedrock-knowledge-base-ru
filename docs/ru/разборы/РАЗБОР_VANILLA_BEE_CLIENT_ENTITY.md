# Разбор Vanilla-примера: client entity пчелы

**Тип материала:** разбор открытого примера Mojang, не копия полного файла.  
**Статус:** структура проверена по исходному sample; поведение в игре в рамках этого разбора отдельно не тестировалось.  
**Источник:** [bee.entity.json в Mojang bedrock-samples](https://github.com/Mojang/bedrock-samples/blob/main/resource_pack/entity/bee.entity.json).

## Зачем нужен этот разбор

Файл показывает, как клиентское описание сущности связывает материалы, текстуры, геометрию, анимации, Molang и render controller. Это хороший пример для чтения архитектуры готового пакета. Он не заменяет серверный Entity JSON из Behavior Pack: визуальная запись отвечает за то, как сущность выглядит и анимируется на клиенте.

## Что видно в образце

В файле используется объект minecraft:client_entity, а внутри description объявлены:

- **identifier** — minecraft:bee, идентификатор существующей Vanilla-сущности. Для собственного моба нужен собственный namespace; не копируйте minecraft:bee как идентификатор нового существа.
- **materials** — материал bee.
- **textures** — несколько визуальных состояний: обычное, злое, с нектаром, а также варианты для детёныша.
- **geometry** — отдельные ключи для взрослой и маленькой модели.
- **animations** — ссылки на анимацию полёта, укуса и другие визуальные движения.
- **particle_effects** — привязка эффекта капель нектара.
- **scripts** — предварительная анимационная логика и выбор корневого контроллера.
- **render_controllers** — передача выбора способа отрисовки контроллеру.
- **spawn_egg** — связь с текстурой яйца призыва.

Это не означает, что все перечисленные возможности обязательны для каждой сущности. Минимальный набор зависит от модели, материалов и требуемого поведения.

## Как проследить одну связь

Возьмите ключ из client entity и найдите его определение в соответствующей папке:

1. Ключ geometry сопоставьте с файлом геометрии и проверьте, что имена костей совпадают с теми, к которым обращаются анимации.
2. Ключ textures сопоставьте с реальными файлами текстур. Проверьте регистр букв и путь.
3. Имена анимаций и контроллеров найдите в файлах animations и animation_controllers.
4. Имена частиц найдите в определениях частиц.
5. Имя render controller найдите в render_controllers и проверьте используемые им ключи материалов, геометрии и текстур.

Если имя упоминается, но соответствующего ресурса нет, клиент может не отобразить нужную часть или записать ошибку в Content Log.

## Практический эксперимент для собственного моба

Не начинайте с копирования полного файла пчелы. Вместо этого:

1. Создайте собственную минимальную client entity с уникальным идентификатором в своём namespace.
2. Подключите одну геометрию, одну текстуру и один материал.
3. Убедитесь, что модель отображается без анимаций.
4. Добавьте одну простую анимацию и только затем animation controller.
5. Добавляйте альтернативные текстуры, частицы и дополнительные контроллеры по одному.
6. После каждого шага проверяйте Content Log и записывайте, что изменилось.

Так легче найти конкретную связь, которая сломалась, чем отлаживать сразу весь сложный файл.

## Что нельзя заключить по одному примеру

- Нельзя считать внутренние ключи bee, названия материалов и идентификаторы ресурсов универсальными для всех сущностей.
- Нельзя заключать, что поле поддерживается во всех версиях только потому, что оно присутствует в текущем sample.
- Нельзя считать отсутствие ошибки JSON доказательством корректной анимации в игре.
- Нельзя переносить файл или ассеты в другой проект без проверки лицензии и требований атрибуции соответствующего содержимого.
