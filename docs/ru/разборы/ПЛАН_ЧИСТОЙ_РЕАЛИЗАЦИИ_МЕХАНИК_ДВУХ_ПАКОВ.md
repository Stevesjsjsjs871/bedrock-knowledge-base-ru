# Чистая реализация механик из Actions & Stuff и Realistic Biomes

Цель — описать функциональные требования сторонних паков и реализовать похожее поведение самостоятельно, понятным собственным кодом. Это не перенос исходников или ассетов оригиналов.

## Clean-room процесс

1. Зафиксировать наблюдаемое поведение, события, входные данные, состояние и результат.
2. Сформулировать требования нейтральным языком.
3. Спроектировать собственные модули, идентификаторы и реализацию; не копировать выражения, обфусцированные функции, тексты, ресурсы или структуру чужого кода.
4. Использовать документированный Minecraft Script API и схемы JSON целевой версии.
5. Для каждой механики указывать статус: обнаружена статически, специфицирована, реализована или проверена в игре.

Публичный репозиторий будет содержать наш самостоятельный код и технические описания. Публичность не означает разрешение публиковать чужие защищённые код, текстуры, модели, аудио или локализацию.

## Realistic Biomes: наблюдения из статического анализа

Архив содержит BP+RP, взаимные зависимости через UUID, 84 JavaScript-модуля и зависимости @minecraft/server 2.7.0 и @minecraft/server-ui 2.0.0. Часть имён обфусцирована, поэтому выводы ниже разделяют наблюдаемое поведение и детали, которые ещё нужно подтвердить.

| Наблюдение | План собственной реализации |
|---|---|
| Шина событий с обработчиками и приоритетами | Собственный EventBus с токенами подписки, отпиской и тестами |
| Проверка уровня разрешений игрока | Централизованный PermissionsService, отказ по умолчанию |
| Переключение Rain/Clear с сообщением и звуковым событием | WeatherService и независимый слой локализованных сообщений |
| Установка времени Sunset, уведомление игрока | TimeService с проверкой доступности API целевой версии |
| Одноразовая выдача предмета при первом появлении игрока с dynamic property | Идемпотентный PlayerInitializer, безопасный при повторном входе |
| Меню справки/формы | Собственная UI-страница, отделённая от игровых сервисов |
| JSON-сериализация и хранилище для мира/сущностей | Собственный StorageService с валидацией и версионированием данных |

Имена внутренних событий и функций оригинала не переносятся. Для точного списка остальных механик нужно проследить импорты, вызовы API, JSON-идентификаторы и связи между файлами.

## Actions & Stuff: что действительно можно извлечь

Архив является преимущественно Resource Pack: в нём есть manifest, entity/particle materials, sounds.json, splashes.json, текстуры и аудио; JavaScript и Behavior Pack не обнаружены. Поэтому не следует приписывать ему отдельную серверную логику без доказательств.

Изучать и воспроизводить собственными примерами можно: анимации и animation controllers; render controllers и геометрию, если они есть; материалы сущностей и частиц; правила выбора визуальных состояний; сопоставления звуков; различия трёх subpacks SP0, SP1 и SP2. Количество ассетов не равно количеству уникальных механик.

## Архитектура нового BP

- scripts/main.js — точка входа и регистрация сервисов.
- scripts/core/event-bus.js — события приложения.
- scripts/core/permissions.js — проверка доступа.
- scripts/services/weather.js — погода.
- scripts/services/time.js — время суток.
- scripts/services/player-init.js — идемпотентная инициализация игрока.
- scripts/services/storage.js — безопасное хранилище.
- scripts/ui/help-menu.js — справка и формы.
- scripts/config/settings.js — настройки и флаги функций.
- tests/ — тесты чистых функций вне игры.

Это предлагаемая архитектура нашей реализации, а не описание внутреннего устройства оригиналов.

## Этапы

### 1. Карта механик
- Разобрать JS-модули BP по импортам, подпискам и вызовам API.
- Индексировать JSON identifier и связи между BP/RP.
- Построить таблицу «наблюдение → требование → публичный API → новый модуль → тест».
- Указывать уверенность и статус для каждого вывода.

### 2. Собственный код
- Написать EventBus с приоритетами, отпиской и обработкой ошибок.
- Реализовать разрешения, погоду и время с проверкой API.
- Реализовать безопасную одноразовую инициализацию игрока.
- Создать собственное меню справки и слой настроек.
- Добавить manifest с новыми UUID и зафиксированной версией API.

### 3. Визуальные механики
- Составить список контроллеров, материалов и JSON-зависимостей Actions & Stuff.
- Создать учебные аналоги на новых identifier и тестовых ресурсах.
- Связать сущности, блоки и предметы BP Realistic Biomes с RP-определениями.
- Не копировать оригинальные текстуры, аудио, модели, локализацию и код.

### 4. Проверка качества
- Проверить синтаксис JSON и отсутствие ссылок на отсутствующие identifier.
- Проверить уникальность UUID.
- Запустить в целевой версии Minecraft и сохранить Content Log.
- Проверить отключение модулей и поведение при ошибках зависимостей.

## Карточка механики

Для каждой механики документировать: название; категорию (Script API, BP JSON, RP JSON, UI или rendering); триггер; входные данные; состояние; результат; ошибки и ограничения; путь нового файла; тест и ожидаемый результат; статус реализации.

## Ограничения

Это статический анализ архивов, а не результат запуска в игре. Часть JS обфусцирована; анализ нельзя считать полным до построения графа вызовов и сопоставления JSON-ссылок. Версия зависимости в manifest сама по себе не доказывает доступность каждого API во всех сборках.
