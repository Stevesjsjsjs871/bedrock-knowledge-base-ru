# События в Script API

> Статус: учебный обзор по официальной документации Stable. Имена конкретных событий и поля event-объектов сверяйте с API Reference для версии модуля в манифесте.

## Событийная модель

Вместо постоянной проверки мира скрипт часто подписывается на событие и реагирует, когда происходит нужное действие. Например, игрок использовал предмет, блок был сломан или сущность погибла.

Подписка обычно строится вокруг объекта события и метода subscribe. В обработчик передаётся объект с данными о произошедшем действии. Его точная структура зависит от конкретного события.

## Основные категории

- **World before events** — события перед некоторыми действиями мира. В таком контексте API может позволять отменить действие, если это предусмотрено событием.
- **World after events** — события после действия или изменения состояния.
- **System before events** — системные этапы жизненного цикла, например запуск, где поддерживаются определённые операции и регистрация.
- **System after events** — системные события, включая получение событий, отправленных через команду /scriptevent.

Не все операции разрешены во всех обработчиках. В частности, официальная документация предупреждает, что API, изменяющие состояние игрового процесса, нельзя вызывать в слушателях некоторых before-событий. Проверяйте ограничения конкретного события.

## Пример подписки

~~~javascript
import { world } from "@minecraft/server";

world.afterEvents.entityDie.subscribe((event) => {
  const deadEntity = event.deadEntity;
  world.sendMessage("Сущность погибла: " + deadEntity.typeId);
});
~~~

Пример иллюстрирует форму подписки и доступ к данным события; перед использованием проверьте точное имя события и поля в версии @minecraft/server, указанной в проекте.

## Перед событием и после события

Не выбирайте before только потому, что он кажется быстрее. Используйте его, когда задача требует реагировать до действия и соответствующее событие поддерживает нужное вмешательство. Для реакции на уже свершившееся действие используйте подходящее after-событие.

Если before-событие поддерживает отмену, проверяйте и обрабатывайте её только по правилам этого события. Не предполагайте, что каждое событие имеет поле cancel.

## Правила хорошего обработчика

1. Делайте обработчик коротким и понятным.
2. Проверяйте тип сущности, предмета или блока до выполнения логики.
3. Не запускайте дорогую работу на каждом тике, если достаточно события.
4. Если действие должно выполняться позже, используйте подходящий планировщик Script API.
5. Не храните ссылки на игровые объекты дольше, чем это безопасно для выбранного сценария.
6. Добавляйте диагностические сообщения на этапе разработки и удаляйте лишний шум перед выпуском.

## Как отлаживать

- Убедитесь, что скрипт загружается и импорт модуля разрешён.
- Проверьте имя события и его доступность в используемой версии API.
- Проверьте, вызывается ли обработчик в нужном сценарии.
- Учитывайте, что before- и after-события получают разные данные.
- Изучите Content Log и ошибки скриптов.
- Проверьте минимальный пример отдельно от остальной логики.
