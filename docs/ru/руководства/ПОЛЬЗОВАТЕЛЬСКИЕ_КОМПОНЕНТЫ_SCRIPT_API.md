# Пользовательские компоненты через Script API

> Статус: обзор по официальному руководству Stable. Подробности регистрации и сигнатуры обработчиков зависят от версии Script API и формата контента.

## Что дают custom components

Пользовательские компоненты позволяют связать JSON-контент с кодом Script API. Они полезны, когда обычных встроенных компонентов недостаточно и требуется реакция на взаимодействие, использование предмета, изменение блока или другое поддерживаемое событие.

Поддержка компонентов и способы регистрации различаются для блоков, предметов и других систем. Не предполагайте, что один и тот же компонент можно подключить к любому типу контента.

## Общая архитектура

В большинстве сценариев нужно согласовать несколько частей:

1. JSON-определение контента содержит ссылку на пользовательский компонент в поддерживаемом формате.
2. Скрипт импортирует нужные API из соответствующего модуля.
3. Регистрация выполняется в подходящем этапе жизненного цикла, например через событие запуска, если это требуется текущей схемой.
4. Компонент предоставляет обработчики, предусмотренные типом контента.
5. Внутри обработчика проверяются входные данные и выполняется ограниченная игровая логика.

Идентификатор компонента в JSON и строка, использованная при регистрации, должны совпадать. Даже небольшая разница в namespace или имени может привести к тому, что обработчик не будет вызван.

## Принципиальный пример регистрации

~~~javascript
import { system } from "@minecraft/server";

system.beforeEvents.startup.subscribe((initEvent) => {
  initEvent.itemComponentRegistry.registerCustomComponent(
    "sample:example_component",
    {
      onConsume(event) {
        // Здесь размещается логика, разрешённая для этого обработчика.
      }
    }
  );
});
~~~

Это схематический пример для объяснения связки регистрации и идентификатора. Сигнатуру события, доступный registry, имя обработчика и допустимые действия обязательно сверяйте с официальным руководством для выбранной версии API. Не копируйте этот фрагмент как универсальный компонент для всех типов контента.

## Ограничения контекста

Обработчики разных типов вызываются в разных обстоятельствах и получают разные данные. Не предполагайте, что у обработчика предмета будут те же поля, что у обработчика блока. Также проверяйте, какие API разрешено вызывать из конкретного контекста.

Если операция должна быть отложена, используйте поддерживаемый планировщик, а не пытайтесь выполнить недопустимую операцию в неподходящем событии.

## Отладка

- Убедитесь, что скрипт успешно загружается.
- Проверьте зависимость модуля в manifest.json.
- Проверьте точное совпадение идентификатора компонента.
- Убедитесь, что регистрация выполняется на правильном этапе.
- Проверьте, что тип контента поддерживает этот механизм.
- Добавьте временную диагностическую запись в обработчик.
- Изучите Content Log и ошибки Script API.
- Проверяйте на минимальном примере, прежде чем добавлять сложную логику.

## Когда использовать custom component

Используйте его, если требуется связать конкретный игровой элемент с программной реакцией. Если задача решается встроенным JSON-компонентом, событием сущности или функцией команд, дополнительный скрипт может быть излишним.
