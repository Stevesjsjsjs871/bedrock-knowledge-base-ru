# Справочник компонентов сущностей: методика полного покрытия

**Статус:** индекс-методика, не замена официальной таблице компонентов. Entity Reference содержит сотни отдельных записей; покрытие должно проверяться по каждой записи и версии.

## Официальная точка входа

- [Entity JSON Documentation — Stable](https://learn.microsoft.com/en-us/minecraft/creator/reference/content/entityreference/?view=minecraft-bedrock-stable)
- [Entity Components Guide](https://learn.microsoft.com/en-us/minecraft/creator/documents/entitycomponentsguide?view=minecraft-bedrock-stable)
- [Entity Components List](https://learn.microsoft.com/en-us/minecraft/creator/reference/content/entityreference/reference/entitycomponents/minecraftcomponent_list?view=minecraft-bedrock-stable)
- [AI Goal Components List](https://learn.microsoft.com/en-us/minecraft/creator/reference/content/entityreference/reference/entitycomponents/ai-goal?view=minecraft-bedrock-stable)

Microsoft отмечает, что список компонентов существенно шире подборки основных компонентов из обзорного руководства. Поэтому несколько общих статей не считаются полным справочником.

## Что фиксировать для каждого компонента

Для каждой отдельной записи следует собрать:
1. Точное имя компонента с namespace.
2. Краткое назначение простым языком.
3. Где компонент допустим и с какими компонентами взаимодействует.
4. Поля, типы данных и вложенную структуру.
5. Значения по умолчанию — только если они подтверждены источником.
6. Минимальную версию или статус Preview, если это документировано.
7. Минимальный JSON-пример, соответствующий текущей схеме.
8. Типичные ошибки и признаки в Content Log, если их можно воспроизвести.
9. Ссылку на конкретную страницу Microsoft Learn и дату проверки.
10. Ссылки на практические примеры Bedrock Wiki или официальные sample packs, если лицензия и происхождение понятны.

## Категории для последовательной обработки

| Группа | Что покрывать |
|---|---|
| Базовые свойства | здоровье, масштаб, физика, столкновения, семейства |
| Движение | движение, навигация, прыжки, плавание, полёт |
| AI goals | цели поведения, приоритеты, условия и цели |
| Цели и атака | выбор цели, атаки, урон и реакция на угрозы |
| Сенсоры и фильтры | обнаружение условий и запуск событий |
| Взаимодействия | предметы, игрок, торговля, приручение и использование |
| Жизненный цикл | рождение, смерть, превращение, сброс и таймеры |
| Визуальные и аудиоэффекты | частицы, звуки, эффекты и привязанные действия |
| Специализированные системы | транспорт, езда, инвентарь, оборудование и уникальные механики |

Категории служат планом работы, а не утверждением, что все компоненты принадлежат только одной группе.

## Статусы покрытия

- not-started — запись ещё не разобрана.
- drafted — создано объяснение, но поля не сверены.
- source-checked — поля и ограничения сверены с официальным источником.
- example-tested — пример проверен в указанной версии игры.
- needs-review — источник или поведение изменились, требуется повторная проверка.
- preview — функция экспериментальная; нельзя описывать её как Stable.

Не ставьте example-tested, если проверяли только синтаксис JSON или просмотрели пример на странице.

## Правила точности

- Не выдумывать отсутствующие значения по умолчанию.
- Не считать необязательное поле эквивалентным полю со значением по умолчанию, если документация этого не подтверждает.
- Не объединять компоненты только потому, что у них похожие названия.
- При слиянии нескольких статей сохранить различия, ссылки и ограничения каждого источника.
- Стабильные и экспериментальные функции описывать раздельно.
- Отмечать, когда пример является схемой для объяснения, а не готовым фрагментом для вставки.

## Следующий практический шаг

Сначала собрать машиночитаемый перечень всех официальных компонентов с URL и метаданными. Затем обрабатывать его пакетами по тематическим группам и отмечать статус каждой записи. Автоматическое извлечение помогает обнаружить пропуски, но не заменяет смысловую проверку и запуск примеров в игре.
