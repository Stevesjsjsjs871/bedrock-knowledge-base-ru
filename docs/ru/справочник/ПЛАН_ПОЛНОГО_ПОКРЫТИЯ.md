# План полного покрытия источников

Этот файл отличает написанные русские объяснения от тем, которые ещё предстоит собрать, сравнить и проверить. Галочка означает только конкретно указанную выполненную работу; она **не** подтверждает полноту всей темы или успешный тест в Minecraft.

## Панель состояния и ближайшие приоритеты

План — рабочий список, а не процент готовности: пункты разного размера, а часть объединяет несколько задач. Не выводите из количества галочек общий процент завершения.

### Как читать статусы
- **Обзор добавлен** — есть начальное объяснение, но поля, версии и исключения могут быть покрыты не полностью.
- **Сверка с источником** — проверены конкретные поля или утверждения с указанием источника.
- **Автоматическая проверка** — проверяется синтаксис/структура/ссылки; это не доказывает поведение в игре.
- **Игровой тест** — есть воспроизводимые шаги, точная версия, платформа и записанный результат.
- **Открыто** — работа не завершена; не трактуйте как подтверждённую функцию.

### Рекомендуемая очередь
1. **Сначала критические пробелы версий и схем:** указать Stable/Preview, точный первоисточник и дату проверки для технических материалов, где это важно.
2. **Затем примеры, влияющие на работоспособность:** сверить поля компонентов, Molang и Script API; проверять примеры на целевой версии там, где доступен игровой тест.
3. **Затем воспроизводимость:** расширить проверенные сценарии BP/RP, пользовательских блоков, частиц и Vibrant Visuals.
4. **Затем полнота источников:** завершать каталоги полей и страниц, разбирать смысловые повторы и документировать исключения.
5. **Community-паки и производительность:** фиксировать оригинальный источник, лицензию, точную версию, конфликты и игровые измерения; не обещать FPS без воспроизводимого замера.

### Конкретные ближайшие задачи

- [ ] Использовать [полнотекстовый поиск по исходникам](../руководства/ПОИСК_ПО_ИСХОДНИКАМ.md) для заполнения открытых пробелов по отдельным полям и API; в карточке сохранять точную ссылку и статус Stable/Preview.
- [ ] Собрать минимальные сквозные примеры для сущности BP + RP, пользовательского блока, предмета/рецепта и Script API: файлы, проверка структуры, шаги в игре и явный статус игрового теста.
- [ ] Для каждого сквозного примера завести короткий список регрессий и не ставить статус «Игровой тест» без версии, платформы, шагов и результата.
- [ ] По диагностическим статьям связать типовые симптомы с первыми проверками и конкретными исходными страницами; объединять существующие объяснения вместо создания новых статей с тем же содержанием.

### Как брать задачу из списка
1. Выберите один открытый пункт и сформулируйте конкретный результат.
2. Найдите связанные страницы в [карте знаний](../КАРТА_ЗНАНИЙ.md) и [каталоге статей](../КАТАЛОГ_СТАТЕЙ.md).
3. Перед правкой проверьте первоисточник, версию и существующие материалы, чтобы не создавать дубликат.
4. Разделяйте статусы документации, анализа исходников, автоматических проверок и теста в игре.
5. После работы обновите соответствующий пункт и добавьте ссылку на результат. Не ставьте галочку только потому, что статья создана.

## Когда считать проект полным
Не называйте проект полным, пока все доступные страницы из заданного охвата учтены в каталоге, у каждой темы есть статус, повторы проверены, а оставшиеся исключения и ограничения перечислены открыто.
